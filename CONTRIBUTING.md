# Contributing to ACOB

Thank you for helping improve ACOB. Contributions to the Django server,
Chromium extension, Python client, MCP adapter, static website, tests, and
documentation are welcome.
Participation in this project is governed by the
[Code of Conduct](CODE_OF_CONDUCT.md).

## Before You Start

- Search the existing issues and pull requests before opening a duplicate.
- Use an issue to discuss substantial features, protocol changes, or breaking
  behavior before investing in an implementation.
- Report vulnerabilities privately as described in [SECURITY.md](SECURITY.md),
  not in a public issue.

## Development Setup

The server requires Python 3.14 or newer and
[uv](https://docs.astral.sh/uv/). The extension requires Node.js 20 or newer
and npm. Chromium 116 or newer is required for extension testing.

Install the server and Python development dependencies:

```bash
uv --directory srv sync
```

Install the extension dependencies:

```bash
npm --prefix extension ci
```

For the standard isolated full-stack installation, run:

```bash
make install ACOB_PROXY_PORT=58346 ACOB_APPLICATION_NAME=default
make install ACOB_PROXY_PORT=61554 ACOB_APPLICATION_NAME=alexandro
```

The default proxy port is `58346`, and `ACOB_APPLICATION_NAME` is required. The installation
context is always `acob-<port>-<name>`; the first example uses Compose project
`acob-58346-default` with a managed browser and ephemeral profile. `ACOB_APPLICATION_NAME`
allows lowercase letters, digits, and internal
hyphens, but cannot start or end with a hyphen. The context prefixes Compose
network, volume, container, and image resources and is the default MCP
registration name used by `install-opencode` and `install-claude`.

Pass the same `ACOB_PROXY_PORT` and `ACOB_APPLICATION_NAME` to `up`, `down`, `purge`, `logs`, and `ps`.
Distinct installations still need distinct ports because only one process can
bind each host port. Names distinguish user or work contexts only: beyond the
per-browser `bid` target they add no protocol routing. Each stack has one global
queue, and any extension polling it may claim any untargeted instruction.

Start the server with migrations applied:

```bash
make -C srv dev
```

Build the extension, then load `extension/dist/` through
`chrome://extensions` with Developer mode enabled:

```bash
npm --prefix extension run build
```

This native workflow keeps the API and MCP development ports at `58347` and
`58348`. Root-installed extensions should instead be loaded from the path
printed by `make install`.

The independently packaged Python client supports Python 3.10 and newer. Its
commands use the project metadata in `client/pyproject.toml`. Install its
development environment with `uv --directory client sync`.

The standalone, non-installable MCP service also supports Python 3.10 and newer
and resolves the client from the sibling project during monorepo development:

```bash
uv --directory mcp sync
```

## Project Layout

- `srv/acob/` contains the Django project configuration.
- `srv/api/` contains the instruction API, validation, persistence, and tests.
- `browser/` contains the Chromium, Xvfb, and optional VNC image.
- `client/` contains the separately packaged asynchronous Python client and its
  tests.
- `mcp/` contains the official-SDK MCP service.
- `extension/src/` contains the TypeScript extension and exported protocol
  types.
- `extension/src/popup.css` is the Tailwind CSS entry point.
- `extension/dist/` is generated by `npm run build` and must not be edited.
- `compose.yaml` is the only Compose file; it defines the `acob-db`,
  `acob-srv`, `acob-mcp`, `acob-proxy`, and `acob-browser` services.
- `database/` contains the Postgres image for the Compose stack (Django owns the
  schema via migrations).
- `proxy/` owns the nginx image and config for single-port routing of API + MCP.
- `PLAN.md` contains the product direction, accepted non-goals, and roadmap.
- `web/` contains the buildless static marketing website.

The browser protocol crosses `srv/api/schemas.py`, `extension/src/types.ts`,
`extension/src/background.ts`, and `client/acob/client.py`. Keep those
contracts aligned whenever an action, payload, result, or validation rule
changes.

The protocol's only executor selector is the optional per-browser `bid`.
REST routes are flat under
`/api/instructions/`, `/api/reinstall/`, and `/api/media/`, and MCP is served at
`/mcp`. Extension settings are local and user-known rather than part of the
server or MCP protocol. Any future network or enterprise design must explicitly
add authentication, executor identity, affinity, leases, and related isolation.

## Making Changes

Create a focused branch from `master`. Prefer small changes with tests that
demonstrate the intended behavior. Preserve the existing public API unless the
change explicitly requires a breaking release.

For extension work:

- Keep runtime code in TypeScript under `extension/src/`.
- Export reusable public contracts from `extension/src/index.ts` and
  `extension/src/types.ts`.
- Use Tailwind utilities in `extension/popup.html` and
  `extension/src/popup.ts`; add shared theme tokens to
  `extension/src/popup.css`.
- Do not commit generated `extension/dist/` files or `node_modules/`.

Create Django migrations for model changes:

```bash
uv --directory srv run manage.py makemigrations
```

Include generated migrations in the same pull request as the model change.

## Verification

Run the checks relevant to your change. Before requesting review, run the full
set when practical.

Server formatting, linting, typing, and tests:

```bash
make -C srv check
make -C srv test
```

Python client formatting, typing, and tests:

```bash
make -C client check
make -C client test
make -C client build
```

MCP service formatting, typing, and tests:

```bash
make -C mcp check
make -C mcp test
```

Extension typing, tests, and production build:

```bash
make -C extension typecheck
make -C extension test
make -C extension build
```

Browser startup-script and image verification:

```bash
make -C browser check
make -C browser build
```

Manually load `extension/dist/` after changes to the manifest, service worker,
offscreen polling, popup, Chrome APIs, or Tailwind styling. Exercise the
affected browser action against a local server.

For website changes, preview `web/` at mobile and desktop widths and verify its
navigation, scenario tabs, focus behavior, and links. Documentation changes
should keep root and component README links valid. Keep MCP tool contracts and
client documentation aligned with server schemas and extension protocol types.

## Pull Requests

- Explain the problem and the chosen solution.
- Link related issues.
- Call out API, storage, migration, security, and compatibility effects.
- List the exact automated and manual checks performed.
- Update documentation and public types with behavior changes.
- Keep unrelated refactors out of the pull request.
